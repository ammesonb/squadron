# Model providers

Command Center owns model-provider connections: credentials, endpoints, and provider-specific connection settings. Squadron configuration only declares which models a workspace is allowed to use.

The name of each `model_provider` block must match a model provider on the workspace's **Settings** page.

## Built-in providers

For Anthropic, OpenAI, and Google Gemini, list the Squadron model keys that configuration may reference:

```hcl
model_provider "anthropic" {
  models = [
    "claude_sonnet_4_6",
    "claude_haiku_4_5",
  ]
}

model_provider "openai" {
  models = ["gpt_5", "gpt_5_mini"]
}
```

Use the block name and allowed key when assigning a model:

```hcl
agent "researcher" {
  model = models.anthropic.claude_sonnet_4_6
}
```

An unlisted model is unavailable to agents and missions, even when the provider account itself can access it.

## OpenAI-compatible providers

Ollama, llama.cpp, vLLM, LiteLLM, and similar servers often use model identifiers that are not suitable HCL keys. Define a mapping from a stable configuration key to the exact identifier sent to the server:

```hcl
model_provider "local" {
  models = {
    llama_3_3    = "llama3.3:70b"
    gemma_4_26b  = "gemma4:26b"
    company_chat = "registry.internal/models/chat@2026-08"
  }
}
```

```hcl
agent "private_researcher" {
  model = models.local.llama_3_3
}
```

`llama_3_3` is the durable key used by configuration. `llama3.3:70b` is the provider model name sent on the wire. This indirection lets an operator update the serving endpoint in Command Center without changing HCL, while model-name changes remain explicit and reviewable in configuration.

## Configure a connection

Open the workspace's **Settings** page in Command Center and add a model provider with the same connection name as the HCL block. A workspace may have multiple connections for the same provider—for example, separate OpenAI accounts or multiple OpenAI-compatible endpoints. Choose one of:

- Anthropic
- OpenAI
- Google Gemini
- OpenAI-compatible

Command Center encrypts API keys in its database. Connected workers receive credentials in memory and do not persist them. Standard providers use their default endpoint unless a base URL override is set. OpenAI-compatible connections require a base URL and may optionally use an API key.

Changing a connection or its credential pushes a new in-memory snapshot to the connected worker and reloads configuration. Credential reveals are restricted to workspace managers and administrators and are recorded in the audit log.

## Migration from `model` blocks

The previous syntax placed provider credentials and endpoints in HCL:

```hcl
model "anthropic" {
  provider = "anthropic"
  api_key  = vars.anthropic_api_key
}
```

Replace it with an allow-list and configure the connection in Command Center:

```hcl
model_provider "anthropic" {
  models = ["claude_sonnet_4_6"]
}
```

On upgrade, Command Center migrates stored `anthropic_api_key`, `openai_api_key`, and `gemini_api_key` workspace values into matching model connections when one does not already exist.
